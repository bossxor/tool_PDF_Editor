# v0.1.2 성능·배포 검증 (2026-10-15)

> **후속 수정 v0.1.3:** 아래 ZIP 단독 배포는 사용자의 설치·기본 PDF 프로그램 등록 요구를 충족하지 못해 철회했다. 현재 기본 배포는 설치 EXE + 포터블 EXE다. 설치 버전의 PDF 연결 등록과 기존 appId는 유지한다. 설치·제거의 앱 실행 확인은 `build/installer.nsh`의 직접 조회로 대체했다. 앱이 실행 중이면 저장·종료를 요청하고, PowerShell/cmd/taskkill 실행과 강제 종료는 하지 않는다. 실제 탐지 규칙은 여전히 미확정이며 검사 통과를 주장하지 않는다. 아래 v0.1.2 측정 결과와 성능 개선은 유지된다. `nsProcess` 반환 코드의 근거는 [NSIS 공식 문서](https://nsis.sourceforge.io/NsProcess_plugin)다.

v0.1.3에서 `npm run test:installer`는 실제 NSIS로 동일한 매크로를 포함한 별도 설치·제거 검사 프로그램을 컴파일한다. 대상 프로세스가 없으면 양쪽 모두 종료 코드 0, 실행 중이면 무인 모드에서 종료 코드 2로 안전하게 중단하는 것을 확인했다. 테스트는 파일 연결·레지스트리·기존 설치본을 수정하지 않는다. 실제 PC에 설치해 Windows 기본 앱 선택을 변경하는 검증은 포함하지 않았다. 설치본은 기존 `fileAssociations`와 NSIS 등록 템플릿을 유지하며, 사용자 기본 앱 설정을 강제로 바꾸지 않는다.

## 재현과 원인

기존 v0.1.1 경로는 `Viewer → PageView → IPC → EngineSession.renderPage`다. 확대율 변경마다 화면 안 페이지뿐 아니라 overscan 페이지도 요청했다. 이전 응답을 UI에서 무시해도 이미 IPC로 보낸 MuPDF 렌더링·PNG 압축은 메인 스레드에서 동기 실행됐다. 큰 페이지와 높은 배율에서 창·IPC 응답까지 지연될 수 있었다. 텍스트 레이어도 배율 변경마다 각 줄에 스타일 쓰기와 `offsetWidth` 읽기를 섞어 레이아웃을 반복 계산했다.

## 수정

- 문서·편집 journal·인쇄를 한 문서별 Node worker가 소유한다. 별도 복사본의 내용 불일치 없이 명령을 순서대로 실행한다. 기존 renderer/preload API는 유지한다.
- 화면 안 페이지만 120ms 후 렌더링한다. 이전 비트맵을 즉시 늘려 표시하고 최신 요청만 적용한다. 페이지마다 진행 중인 요청은 하나로 제한한다. 이미 진행 중인 WASM 연산을 강제 중단하지는 않는다.
- 화면 비트맵은 약 8MP 및 변 길이 8192px로 제한한다. 픽셀 경계 반올림으로 8MP를 소폭 초과할 수 있다. 요청한 CSS 크기·PDF 좌표를 유지하며 인쇄에는 이 제한을 적용하지 않는다. 고배율 선명도는 이 절충의 한계다.
- PNG 캐시는 문서별 최대 32MiB·64개이며 모든 편집·undo/redo·문서 열기에서 무효화한다. 렌더링용 page/pixmap과 화면 object URL을 정리한다.
- 텍스트 줄은 PDF 좌표에서 한 번 측정하고 부모 레이어만 배율 변환한다. DOM 읽기·쓰기를 묶는다. 확대·축소와 창 크기 변경 시 기존 페이지 내 읽기 위치를 유지한다.

## 측정

Windows x64 로컬의 4페이지 PDF를 사용했다. 문서와 문서명은 업로드하지 않았다. `scripts/profile-engine.mjs`는 각 배율마다 문서를 다시 열어 캐시를 비우고 4페이지를 순차 렌더링한다. 아래는 한 번의 전후 측정이며 통계적 평균이나 모든 PDF의 속도 보장은 아니다.

| 배율 | v0.1.1 | v0.1.2 | 페이지당 최대 픽셀 (전 → 후) |
| --- | ---: | ---: | --- |
| 100% | 250ms | 273ms | 501,832 → 501,832 |
| 200% | 398ms | 401ms | 2,005,644 → 2,005,644 |
| 400% | 1,143ms | 1,204ms | 8,022,576 → 8,002,956 |
| 800% | 3,647ms | 1,418ms | 32,083,568 → 8,002,956 |

800%의 렌더링 시간은 약 61%, 픽셀 수는 약 75% 감소했다. 보통 배율의 단일 렌더링 자체는 유의미하게 빨라졌다고 주장하지 않는다. 주된 개선은 메인 스레드에서 무거운 처리를 분리하고 불필요한 중간 요청을 없애는 것이다.

생성한 복잡한 벡터 PDF를 실제 worker에서 렌더링한 테스트에서는 1,064ms 동안 메인 스레드 10ms 타이머가 67회 실행됐고 최대 간격은 21ms였다. UI 테스트의 가짜 API 계측에서는 16ms 간격의 휠 입력 20회가 최종 페이지 렌더 요청 1회로 합쳐졌다. 이 UI 요청 수는 실제 PDF 렌더 시간 측정과 구분한다.

## 제거 프로그램 조사와 배포 변경

사용자는 차단 대상이 앱 제거 프로그램이라고 확인했다. 코드에서 PDF 페이지·주석 삭제는 MuPDF API를 직접 호출하며 외부 삭제 실행 파일이나 셸을 사용하지 않는다. 기존 Windows 설치·제거 프로그램은 electron-builder의 NSIS 기본 템플릿에서 생성되며, 기존 설치 EXE의 Authenticode 상태는 `NotSigned`였다. 이 PC의 Defender 이벤트 1116 조회에는 일치하는 기록이 없었고, 해당 백신의 탐지명·차단 파일 해시도 확보되지 않았다. **정확한 탐지 규칙이나 오탐 여부는 확정하지 못했다.**

[NSIS 공식 문서](https://nsis.sourceforge.io/NSIS_False_Positives)는 NSIS 산출물의 오탐 사례를 안내하지만, 이것이 이번 탐지의 원인이라는 증거는 아니다. 설치·제거 방식은 [electron-builder 공식 NSIS 문서](https://www.electron.build/docs/nsis/)를 기준으로 조사했다.

v0.1.2의 기본 배포는 일반 ZIP이다. 설치·제거 EXE나 자동 압축 해제 런처를 배포하지 않고, 압축 해제한 앱 폴더에서 직접 실행한다. 제거는 앱 종료 후 그 폴더만 삭제한다. 기존 설치본을 강제 제거하거나 사용자 문서·설정을 지우지 않는다. 자동 파일 연결·바로가기 등록도 없다. 기존 설치본을 제거하지 않아도 별도 폴더에서 사용할 수 있다.

백신 예외 등록, 실시간 감시 해제, 탐지 회피용 이름 변경·난독화·패킹은 적용하지 않았다. 새 파일도 코드 서명 인증서가 없어 서명되지 않았고, 모든 보안 제품의 미탐지를 보장하지 않는다. SHA-256은 무결성 확인용이다. 기존 NSIS 빌드는 개발자의 호환성 조사용 `npm run dist:installer`로만 남겨 두고 기본 릴리스에는 포함하지 않는다. 기존 제거 프로그램 자체의 탐지 해소는 해당 탐지 정보와 공급사의 판정이 필요하다.

완성한 ZIP의 Defender 사용자 지정 검사를 시도했으나 `MpCmdRun.exe`가 `0x80508023`으로 종료되어 검사 결과를 얻지 못했다. 따라서 백신 검사 통과 또는 오탐 해소로 기록하지 않는다. 보안 설정은 변경하지 않았다.

## 검증 범위와 재실행

- `npm run typecheck`
- `npm run test:engine`: 실제 worker/WASM, 반복·고배율·잘못된 요청, 메인 스레드 응답, 텍스트·검색, 주석 삭제, 페이지 삭제·undo/redo, 캐시 무효화, 저장·재열기, 추출·병합·재정렬, 암호화·인증, 탭 격리
- `npm run test:ui`: 초기 맞춤·가상 페이지 이동·창 크기 변경, 연속 확대·축소 병합, 느린 요청·실패 복구, 현재 페이지 유지, 텍스트 선택 좌표
- `npm run test:app`: 가짜 API 없이 실제 main/preload/renderer/worker의 문서 열기·비트맵·텍스트·확대·삭제·undo·탭 종료
- `npm run dist`: 일반 ZIP 및 SHA-256 생성
- `PDF_EDITOR_APP_ROOT=dist/win-unpacked/resources/app.asar` 환경으로 실제 앱 통합 테스트를 재실행해 패키징된 worker/WASM 로딩도 확인 (PowerShell에서는 `$env:PDF_EDITOR_APP_ROOT`로 절대 경로 지정)

테스트가 생성하는 PDF와 캡처·측정 JSON은 `.verification/`에만 저장한다. 인쇄 검증은 주석 포함 인쇄용 비트맵 생성까지이며 실제 프린터 출력은 포함하지 않는다.
